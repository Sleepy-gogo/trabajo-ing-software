SERA · revisión técnica

Usuarios ya tiene una base que se puede repetir.

La rama pasó de un modelo que no arrancaba a un módulo BCE completo para administración de usuarios. Este informe deja por escrito los errores, las correcciones y las reglas que conviene repetir.

28 tests aprobados Flyway y arranque verificados Autenticación pendiente de redefinir

Resultado

El módulo cubre el trabajo compatible con las decisiones actuales de TRA-19, TRA-22 y TRA-24. Tiene entidad, migración, repository, service, DTOs, controller, errores consistentes, búsqueda, baja lógica y pruebas. rol y qrUsuario son textos simples. No hay catálogo de roles ni rotación de QR.

  • La API nunca recibe ni devuelve la entidad JPA.
  • Email y DNI tienen validación de unicidad en Control y restricciones en PostgreSQL.
  • Las contraseñas se guardan con BCrypt y no aparecen en responses.
  • La baja cambia el estado a INACTIVO; no borra el historial.

Mi recomendación

No empezar login ni users/me hasta reescribir TRA-20 y TRA-21. Esas tareas todavía exigen RBAC y un modelo de perfil que el equipo ya descartó. Implementarlas hoy volvería a meter decisiones inventadas en el código.

El problema no era una clase aislada. La rama había empezado por escribir archivos sin cerrar el recorrido vertical ni ejecutar el build.

La lección incómoda

Checklist para los próximos módulos

  1. Separar hechos de deseos

    Antes de escribir una entidad, anotar qué pide una consigna vigente y qué salió de un mock, un documento generado o una idea del equipo. Si no hay acuerdo, la tarea no está lista para programar.

  2. Cerrar un recorrido vertical pequeño

    Entity, migración, repository, Control, DTOs, Boundary y dos o tres pruebas que cubran decisiones reales. No dejar media feature repartida entre capas.

  3. Proteger el dominio

    Evitar setters generales. Dar nombres a los cambios de estado. Normalizar los datos en un solo lugar y duplicar en la base las restricciones que protegen integridad.

  4. Revisar el diff antes del commit

    Un POM entero reindentado, un puerto cambiado sin docs o una dependencia sin uso deberían saltar a la vista con git diff --stat y git diff.

  5. Ejecutar el mismo cierre siempre

    cd apps/api
.\mvnw.cmd spotless:apply
.\mvnw.cmd verify

cd ../web
pnpm lint
pnpm typecheck
pnpm build

cd ../..
docker compose config
git diff --check
git status --short

  6. Probar la migración de verdad

    Cuando cambia el schema, levantar PostgreSQL y arrancar Spring. Un test unitario no demuestra que Flyway y Hibernate estén de acuerdo.

  7. Commits que expliquen una sola cosa

    Usar Conventional Commits y mencionar la tarea en el cuerpo. No mezclar formato, comportamiento, documentación y una migración ajena si pueden revisarse por separado.

No integrar si

El branch falla verify, expone una entidad JPA, guarda contraseñas sin hash, modifica una migración ya consolidada o implementa reglas que el equipo todavía discute.
